# Dissertation security remediation — November 2026

## Behaviour changed

- Department managers' attendance and employee listings are constrained before querying. Weekend duty only grants cross-department access to the active scheduling picker, not the full employee management list. National identifiers in active pickers are masked.
- Schedule creation and deletion enforce actor scope. Only a system administrator can create or manage system administrator privileges. Self-demotion/suspension through employee editing is blocked.
- Department messages capture the sender's department at creation. Moving an employee does not move the historical audience. Sender and senior management retain access; other departments cannot list, delete or download those messages. Senior management oversight is explicit in the UI. Historical messages with no captured department are sender/senior-management only. Accounts without a department cannot send department messages. Organisation-wide notices use announcements.
- New attachments are stored transactionally in PostgreSQL, so they share the message backup/restore boundary. Old files remain readable from ATTACHMENTS_DIR after permission checks. Those old files must still be backed up separately. Attachment responses force downloads, and both clients send authentication on download. Signatures and bounded Office ZIP structures are checked. Legacy .doc/.xls and macro-bearing Office archives are rejected. This is not antivirus scanning or proof that a file is harmless.
- Browser refresh credentials use Secure, HttpOnly, SameSite=Lax cookies; access tokens stay in memory. Native clients retain SecureStore. The browser route requires a custom header, and credentialed CORS rejects wildcard origins. Native auth endpoints remain compatible. Refresh is single-flight per tab and uses Web Locks across tabs when available. The web app and API must be same-site HTTPS in production (the configured asa-force.com hosts meet this design).
- Failed login/OTP counters commit on rejection. Account locks and refresh rotations use database row locks. Refresh reuse revokes the token family even when the API rejects the request. Password changes/reset and logout-all invalidate prior access credentials through a credential-version claim. Existing access tokens must be renewed after upgrade. Initial-password restrictions are enforced by the backend.
- Production rate limits use atomic PostgreSQL fixed-window counters shared across instances and restarts. Development uses atomic in-memory sliding windows. Trusted proxy matching uses actual CIDR matching, never string prefixes. No proxy ranges are guessed.
- Attendance uses Asia/Riyadh by default, requires an assigned working day, opens 10 minutes before the shift, and closes at shift end. The late grace period remains 15 minutes. Check-in/out serialize on the employee row. Schedule creation supports same-day shifts; overnight shifts are explicitly rejected pending a full overnight workflow. Sunday is the supported week start. The mobile home now offers check-out as well as check-in.
- English employee names are optional and editable alongside Arabic names. Mobile leave API calls, dependency compatibility and authenticated file handling were repaired.
- Audit records are written after a business commit in a separate transaction instead of relying on self-invoked transaction/async annotations.

## Controlled upgrade (required before deployment)

1. Back up PostgreSQL and any legacy attachment directory. Rehearse the upgrade and restore on a separate environment. Do not merge/deploy this branch directly onto production without this preparation.
2. V21 and V22 no longer contain fixed administrator credentials or personal identifiers. Their checksums intentionally differ from old deployments. Compare the release diff and migration history. For an existing database only, explicitly enable `APP_MIGRATIONS_REPAIR=true` for one reviewed migration run; remove it immediately afterwards. Automatic repair is now disabled. Never use repair to conceal an unexplained mismatch.
3. V28 suspends SYSTEM_ADMIN accounts whose initial password is still marked unchanged, and revokes their refresh sessions. Changed accounts are preserved. Rotate any known exposed credentials; this release does not rewrite Git history or rotate live deployment secrets.
4. If there is no active system administrator, enable `APP_BOOTSTRAP_ENABLED=true` once and supply `BOOTSTRAP_NATIONAL_ID`, `BOOTSTRAP_PHONE`, `BOOTSTRAP_FIRST_NAME`, `BOOTSTRAP_LAST_NAME` and a unique `BOOTSTRAP_PASSWORD` of at least 16 characters through deployment secrets. Disable bootstrap and remove the temporary secret after creation. The account must change its password. Bootstrap refuses to run when an active system administrator already exists.
5. Supply `GEOFENCE_LATITUDE`, `GEOFENCE_LONGITUDE` and optionally `GEOFENCE_RADIUS_METERS`. Development/test coordinates are fictional. Set only verified `TRUSTED_PROXY_CIDRS` for your actual proxy infrastructure. Do not trust arbitrary forwarding headers.
6. Supply `CREDENTIAL_DELIVERY_URL` and `CREDENTIAL_DELIVERY_TOKEN`. The HTTPS gateway contract is POST JSON `{ "to": "phone number", "message": "SMS text" }`, authenticated by a Bearer token, with a 2xx response only after acceptance. Connect this adapter to the organisation's SMS provider. Production startup refuses missing gateway configuration or console credential logging. No live SMS was sent during this work; actual delivery and provider failures must be exercised in staging.
7. Apply the new migrations, deploy the matching web client/API, and verify cookie login, refresh, logout, password reset, departmental permissions and attachment downloads in the actual HTTPS deployment. Backups containing new attachments must include `message_attachments`.

## Remaining external or research work

Nafath is not implemented: onboarding, approved protocol documentation, credentials and a test environment are required. It must not be simulated as successful identity verification. Employment approval and application permissions remain separate from national identity.

Live SMS deliverability, real-device location accuracy, usability/accessibility studies with participants, production load measurements, antivirus scanning, external monitoring/alert routing, and a timed production-scale recovery exercise are not established by automated tests. Geofencing still does not prove physical presence. Device attestation, privileged MFA and certificate pinning remain separate future enhancements.

## Verification

Local verification on 10 November 2026 passed: 18 backend tests against PostgreSQL 16 with all 30 migrations, 98 mobile tests across 13 suites, both client TypeScript checks, and the web production build. The additional interactive browser smoke test was not completed because approval review hit an account usage limit. These results do not establish production readiness or live-provider compatibility.

The repository includes regression coverage for failed authentication persistence, account lockout, refresh reuse, inactive-account renewal, attendance scope, employee scope, department message visibility, attachment access and validation, cookie/CSRF boundaries, attendance window boundaries and concurrent rate limiting. `PostgresRateLimitTest` runs when the PostgreSQL driver property is explicitly set. Default local tests use H2; CI uses PostgreSQL 16 and applies all migrations.

Use Java 17 (the project's compiler target), not the machine's unrelated default JDK. Run `mvn -f backend/pom.xml test` for the local suite. `.github/workflows/verify.yml` contains the full PostgreSQL invocation and client commands. Mobile tests use native module mocks and do not substitute for device or user studies.
